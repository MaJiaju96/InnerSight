# 内观（InnerSight）项目书

版本：v0.7 | 日期：2026-11-25 | 状态：主项目优先；S0 从通用后台开始，训练与二期方向沿用既定规划

## 1. 项目定位

正式拟题：**内观（InnerSight）：面向 Java 工程师的 AI 模拟面试与知识自省系统**。

中文名「内观」取意于道家的内观理念，意为内视自身、自省自身。英文名 InnerSight 用作副标及工程名称。

主要面向开发者个人使用，通过自己维护的题库和评分依据，进行固定笔试、模拟面试和知识复盘。开发项目本身也是 Java 工程能力的学习过程。

核心目标：知识覆盖可控、追问过程可控、评价依据可追溯。

本项目书确定长期目标、主项目职责和阶段边界。每项独立需求用需求分析书拆解业务规则，用 PRD 确定本次流程及验收条件；UI 跟随当期 PRD。开发对照已确认的 PRD、引用的需求条款和对应 UI。S0 先搭建通用后台，再交付文字训练与复盘；卫星系统不构成启动条件。

## 2. 背景与问题

以下背景来自项目发起人的实际使用体验，不代表对所有市场产品的调查结论。

| 当前体验中的问题 | InnerSight 的应对方向 |
|---|---|
| A/B/C 题目比例固定，无法按自身需求调整 | 固定套题与可配置比例组卷分别支持 |
| 按试卷逐题执行，缺少原理与场景深挖 | 回答驱动的追问，明确目标和预算 |
| 通用 AI 多轮训练偏向重复方向 | 显式选题计划、本轮知识状态和追问边界 |
| 过去答过的内容被默认掌握 | 跨轮历史不自动豁免本轮考察 |
| 长回答覆盖了多个问题，仍被重复提问 | 回答映射到多个知识点，调整后续问题 |
| 评价依赖标准答案或模糊印象 | 结构化评价标准、原话证据与不确定标记 |

面试知识既用于求职，也用于理解线上故障、性能瓶颈和方案权衡。题库逐步加入工程场景，使记忆结论与实际分析能力能够分别验证。

## 3. 目标用户与价值

第一阶段用户：项目发起人及类似需求的 Java 开发者。训练仍面向个人使用；同一实例可有多个后台账号，按角色控制管理操作。后台账号不引入团队训练、商业运营或招聘筛选流程。

- 学习者：看清概念、原理、边界和场景应用分别掌握到什么程度。
- 题库维护者：积累可信资料、评价要点和可复用的追问方向。
- 项目开发者：通过真实业务练习数据建模、状态流转、异步调用、失败恢复和可观测性。

## 4. 产品能力与范围

| 阶段 | 能力 | 完成标志 |
|---|---|---|
| S0：工程骨架与通用后台 | 前后端与数据库真实联通，基础登录、权限、用户和角色管理 | 从空环境启动；管理员可开通、授权和撤权，另一账号只能使用获授权的管理操作，无需模型或训练数据 |
| S1：业务基础 | 题库维护、发布版本、套题、出题前配置确认、规则组卷、训练记录 | 不配置模型也能按已确认的难度配额组卷、完成笔试并回看回答 |
| S2：最小完整闭环 | 文字面试、长回答识别、有限追问、证据评价、复盘 | 用少量人工标注的回答核对评分与追问；模型失败后回答仍可恢复 |
| S3：主项目增强（候选） | 扩充评价样例、复测、自评、批量导入和资料检索 | 按实际训练中发现的误判或复习困难，选定当期目标并验证改进 |

S0 搭建骨架，MVP 由 S1 和 S2 构成。主项目闭环跑通后，才按实际需要考虑卫星系统与独立验证项目；两者都不列入当前交付计划。主项目自身的测试与评价样例随功能交付。

第一阶段不安排自动采集热点、自动生成未经审核的正式题库、组织与多租户权限体系、支付、排行榜或生产级微服务部署。

### 出题前配置确认与两种出题方式

训练前可手填工作年限、岗位方向（前端、后端、全栈等）和工作侧重点（功能开发、维护排障、性能优化等），也可上传简历补充项目经历。方向和侧重点可以组合。年限与简历只用于建议考什么，不作为能力证明或评分依据。首批题库仍以 Java 为主。

**先确认配置，再出题。** 用户可修改手填或 AI 识别的要点，选择出题方式、题目范围、总题数，以及单一难度或 A/B/C 混合比例。混合比例合计为 100%，确认时显示各等级对应的题数；本场只采用用户确认的配置。简历可跳过；使用外部模型识别前，由用户确认要发送的经历或技能片段，联系方式等无关信息不发送。

| 出题方式 | 如何形成当场题目 |
|---|---|
| 规则匹配 | 按用户确认的岗位、训练重点与题库标签匹配已发布题目，按等级配额抽取。整条路径无需模型；候选不足时显示缺口，由用户调整。 |
| AI 识别与自动出题 | AI 可从用户提供的背景中提取可编辑的训练重点；确认配置后，可选用库内题，也可在用户允许时围绕项目经历生成新题及评价要点。主系统校验范围、等级配额和重复题；生成题标注来源，仅用于本场，审核后才可进入正式题库。 |

这两种方式用于需要组卷的训练；选择固定套题时沿用已发布的题目与顺序。未启用模型或 AI 出题失败时，用户可保留配置切换到规则匹配，继续作答、保存和回看；依赖模型的动态追问和自动评分分别提示不可用或待评价。AI 出题的接入阶段、简历格式与解析方式留给当期 PRD。

### 二期规划：跨岗位协作与独立交付

首期 Java 面试与复盘闭环完成后，以真实项目为素材，帮助开发者了解产品、UI 设计、测试、运维等岗位的日常职责、工作方法和面试关注点。通过完成并复盘从需求澄清、产品规划到开发、测试和上线维护的具体任务，练习跨岗位协作，逐步具备独立交付项目的能力。

具体覆盖哪些岗位、如何训练和验收，留到二期 PRD 确定。

## 5. 关键设计原则

1. Java 业务规则执行或校验已确认的组卷配置，控制追问预算、停止和切换；AI 可提供候选题、回答分析、追问与评价建议。
2. 题目关联知识点，回答产生知识点证据。一次回答可以验证多个点。
3. 当前题目得分与扩展知识展示分别呈现。多说不自动多得分。
4. 历史用于复习安排，本轮评价依据本轮证据。
5. 正确、部分掌握、未体现、明确错误、未考察和待确认分别记录。
6. 规则、题目与模型配置可追溯；保留回答原文，不以摘要替代证据。
7. 自建题库、回答与评价证据是长期学习资产。保留题库导出和备份恢复的目标；更换模型或停用扩展后，仍能回看历史训练使用的题目、回答与评价依据。

### 可插拔的定义与边界

**可插拔**指某项外围能力可以接入、替换或停用，而无需改写组卷、会话推进和评分规则。主项目拥有正式题库、已提交回答和历史报告，决定发布什么、下一题问什么、如何计分。扩展只通过主项目提供的入口交付结果，不直接写主库。

| 后续方向（举例） | 扩展可提供什么 | 停用后主项目仍能做什么 |
|---|---|---|
| 语音识别 | 转写草稿，由用户确认后作为回答提交 | 照常用文字作答，回看原有评价 |
| GitHub 资源接入 | 带来源的候选题目或行业动态线索，由维护者决定是否采用 | 使用已发布题库训练，面试不等待在线同步 |

首期以应用内模块组织当期能力，不为上述方向预建插件框架、通用接口或远程服务。具体扩展准备立项时，再讨论数据范围、对接方式与失败处理；有独立使用、部署或性能需求时，再决定是否拆为单独系统。

## 6. 技术方向

前端采用 Vue + TypeScript，后端采用 Spring Boot 模块化单体。主数据库确定为 **MariaDB Server 10.11.19**，开发和验收使用同一服务端版本。连接、迁移及实库验证见[技术方案书](02-technical-design.md)。进入模型接入阶段时再引入 LangChain4j。

先在一个后端应用中划分身份与后台管理职责，再随当期需求加入题库、组卷、训练会话、回答分析、评价、复盘及 AI 接入。S0 不依赖模型服务。

各组件的职责如下。标为「候选」的组件按实际需求或测量结果决定是否引入。

| 组件 | 规划职责 |
|---|---|
| MariaDB Server 10.11.19（主库） | 后台用户、角色与授权，以及后续的题目、训练记录、评价和版本快照 |
| LangChain4j | 组织模型请求、结构化结果和按需资料检索 |
| ES，候选 | 全文与向量检索，索引从主数据重建 |
| Python 服务，候选 | 有明确工具或部署需要时提取 AI 能力 |
| Spring Cloud，候选 | 业务和学习目标需要时拆分服务 |

库内题按题目版本加载评价标准；AI 为本场生成的新题随训练保存题干、评价要点与来源，未经核验的要点明确标注。需要补充跨知识点资料时再使用检索。初期不要求全量向量化或 GraphRAG。

## 8. 效果验证

统计口径先明确，再设目标值。首批样例必须覆盖简短准确、冗长错误、合理替代答案、跨题扩展、前后矛盾、提示后答出和资料版本不匹配。

出题验收示例：三年后端经验、侧重维护排障，确认 10 题，A/B/C 为 20%/50%/30%。两种方式生成的可用试卷都应为 2/5/3 题；关闭模型、候选题充足时，规则路径仍能按同一配置完成组卷。候选不足时应提示缺口，不自动更改比例。

| 指标 | 建议统计方式 |
|---|---|
| 组卷正确性 | 实际题目、等级与配置及不足策略一致的次数 / 全部组卷次数 |
| 覆盖识别准确性 | 按知识点与人工标注比较，记录漏识别和误识别 |
| 无依据评价率 | 找不到原话或规则依据的判断数 / 全部判断数 |
| 重复基础追问率 | 本轮已充分解释却再次被同层询问的次数 / 全部追问次数 |
| 开放答案误判 | 合理替代路径被判错的样例数与原因 |
| 可恢复性 | 失败后未丢回答、未重复推进会话的样例是否通过 |

模型评价的稳定性需在选定模型上实测。总分不用于未经校准的用户间排名。

## 9. 风险与应对

| 风险 | 应对设计 |
|---|---|
| 题库错误或过时 | 来源、适用版本、人工审核、发布快照 |
| 模型误判与偏好长回答 | 独立评价步骤、原话证据、人工样例与重评 |
| 模型超时、成本上升 | 请求预算、超时、受控重试与费用记录 |
| 长回答丢失或覆盖遗漏 | 先持久化原文，逐点记录证据，按需读取上下文 |
| 为学习技术扩大范围 | 以核心闭环验收推进，扩展项单独立项 |
| 用户回答改变模型指令 | 回答作为待分析数据；会话动作由程序校验 |
